# Google 帳號登入 + 跨裝置雲端同步 — 設計文件

日期：2026-09-13

## 背景與問題

目前資料只存在本機瀏覽器的 IndexedDB，換裝置得靠手動「匯出備份 JSON → 傳到新裝置 →
匯入」。這份文件記錄的需求：讓**同一位老師**能透過登入 Google 帳號，讓自己的資料在
不同裝置間自動同步，取代手動匯出/匯入這個動作，同時保留現有的離線／訪客使用方式。

## 範圍

- **只涵蓋 PWA 版**（`npm run build:web` → `site/`／repo 根目錄的 `index.html`）。離線版
  （`dist/TableC.html`）完全不動、不加任何登入/同步相關程式碼。
- **單一使用者跨裝置同步**，不是多位老師共用同一份資料的多人協作系統。不需要處理
  「兩個不同的人同時編輯同一個孩子的紀錄」這種多使用者權限/共享問題。
- 不強制登入：不登入（訪客模式）也能完整使用本機資料、手動匯出/匯入，跟現在行為
  一致。登入只是額外選項。

## 前置條件（新 session 開始實作前，需要先在 code 之外完成的事）

1. **需要一個 Google Cloud 專案**，啟用 Google Drive API、設定 OAuth 同意畫面、取得一個
   OAuth Client ID（給 Google Identity Services 用）。這一步需要人用自己的 Google 帳號
   登入 Google Cloud Console 操作，Claude 沒辦法代為建立，需要先請使用者完成，把
   Client ID 準備好。
2. **資料庫 schema 需要補上「最後修改時間」欄位**：目前 `src/storage/db.js`、
   `parentReportDb.js`、`monthlyPlanDb.js` 底下多數資料表只有 `createdAt`，沒有每筆
   記錄一個 `updatedAt`。逐筆比對、判斷「誰的比較新」都要靠這個欄位，必須在做同步邏輯
   之前，先幫每個會被同步的資料表（Child、AssessmentForm、ObservationEntry、
   ParentReport、CoursePlanEntry、DevelopmentRecordEntry、BehaviorObservationEntry、
   HighlightEntry）補上 `updatedAt`，每次寫入時更新它。

## 身份驗證 / 登入流程

- 沿用現有密碼保護（`src/auth/passwordGate.js`）不變，密碼輸入正確之後才會看到下面的
  畫面。密碼保護本身要不要調整，留到正式上線前另外處理，這次不動。
- 密碼過了之後，**第一次**（尚未選擇過登入方式時）顯示一個新的登入選擇畫面：
  「使用 Google 登入」或「以訪客身份繼續」。選過之後記住這個選擇（跟現有訪客警告視窗
  記住選擇同一套邏輯），下次密碼過關後直接進正常畫面，不再重複詢問。
- **已用 Google 登入**：標題列、備份按鈕左邊顯示問候語 + 名字，例如「早安，小美」。
  - 時段切分：05:00–11:59 早安、12:00–17:59 午安、18:00–04:59 晚安。
  - 名字直接用 Google 帳號本身的顯示名稱，不另外讓使用者自訂稱呼。
- **訪客模式**：標題列、備份按鈕左邊顯示一個「使用 Google 登入」按鈕，讓使用者隨時
  可以改成登入。
- **離線時按登入**：顯示「目前離線，暫時無法登入」，不要讓按鈕呈現卡住/無反應的樣子。
- **登出**：只是停止同步，**不清除本機已同步下來的資料**（這是老師自己的裝置，不是
  共用裝置的情境，登出更接近「先暫停」）。

## 儲存位置

存在使用者自己 Google 雲端硬碟裡「看得到」的一般資料夾（不是隱藏的 App 專屬儲存區），
讓老師自己也能在雲端硬碟網頁上看到這個檔案、需要的話能自行額外複製一份。

## 同步機制

- **自動同步**，兩個觸發點：(1) 存檔後（debounce 一下再送出，避免每個按鍵都觸發網路
  動作）；(2) App 開啟／從背景切回前景時。
- **只更新不同的地方**，不是整包資料覆蓋掉重傳：逐筆比對本機與雲端，只有真的不一樣的
  記錄才需要動作。
- **首次登入合併**：只有「兩邊都有、但內容不同」才需要跳出比較畫面詢問使用者；只有
  一邊有的記錄（本機獨有／雲端獨有）直接自動合併，不用逐筆詢問。換新裝置登入時，既有
  雲端資料會直接補齊下載。
- **下載採「一筆存一筆」，可中斷續傳**：換新裝置第一次同步資料量較大時，不要等全部
  下載完才一次寫入本機，避免中途斷線就要整個重來。已寫入本機的部分視為完成，之後只
  補還沒同步到的部分。
- **傳輸建議同時傳多個檔案**（例如一次 4~6 個並行），不要一個一個排隊傳，減少每個
  檔案本身的請求延遲累加起來的等待時間。

## 衝突偵測與解決

- 判斷「誰比較新」不能只信裝置自己的時鐘（裝置時間可能飄移不準），要以雲端記錄的時間
  為準。
- 偵測到「同一筆記錄，兩邊都改過、內容不一樣」時，跳出畫面顯示兩邊的差異，讓使用者
  選擇：保留 A、保留 B、或都保留。
  - 「都保留」= 產生兩筆記錄，並標記「待確認／曾經衝突」，讓使用者事後自己整理，
    系統不自作主張猜測合併結果。
- **不是所有「兩邊都改了」都算衝突**：例如一台裝置新增了照片、另一台改了同一則點滴
  分享的文字說明，這是改動了不同的欄位，應該自動合併成「新照片＋新文字都保留」，
  不需要跳出比較畫面。只有「兩邊都改了同一個欄位、內容還不一樣」才算真衝突。

## 照片同步

- 照片跟文字資料一樣走「只傳新增/修改的部分」：每張照片存進本機時標記「尚未同步」，
  同步時只找這些記錄來傳，傳完標記為「已同步」，不需要每次同步都整批重新比對。
- 照片本身一般不會被「編輯」，只有「換一張」；文字說明改了但照片沒換時，只傳文字，
  不重傳照片本體。
- **刪除會同步**：本機刪除的照片，雲端那份也會跟著刪除（避免換裝置登入時，把已經
  在別台裝置上特意刪除的照片又還原回來，造成「刪了又跑出來」的困惑）。
- 為避免「同步刪除」帶來的誤刪風險，靠兩個現成/低成本的安全網，**不做**通用的「回上
  一步」復原功能：
  1. 透過 Google 雲端硬碟本身內建的版本歷史機制更新雲端檔案，Google 自動保留過去
     30 天的舊版本，可直接在雲端硬碟網頁介面還原，不用自己寫版本記錄邏輯。
  2. 刪除採**軟刪除 + 30 天緩衝期**（本機與雲端都先標記刪除、放進「最近刪除」，
     30 天後才真的清除），而不是刪了立刻消失。

### 照片壓縮設定

- 維持 JPEG 格式，**不換成 WebP**：專案用的 `docx` 套件（v9.0.2）內建只認得
  `jpg`／`png`／`gif`／`bmp` 四種圖片格式（已在 `node_modules/docx/dist/index.d.ts`
  確認過），WebP 不在其中，換格式會導致每次匯出 Word 檔前都要多一道「解碼再轉回
  JPEG」的手續，多一個可能失敗的環節，換到的空間節省(~25~30%)不划算。
- **把 `src/media/imagePreprocess.js` 的 `compressImage` 預設 `maxEdge` 從 1600 調
  小到約 960**：查過 `src/export/parentReportDocxExport.js` 的排版邏輯，點滴分享
  照片在 Word 文件裡實際顯示寬度最大約 717px（一排只放一張的情況），現在存 1600px
  完全用不到那個解析度。調到 960px 之後，檔案大小可以縮到約 1/3，且是真正零視覺
  損失（因為從來沒有地方會顯示到超過 960px 的解析度）。
- **只影響以後新上傳的照片**，已經用舊設定存過的既有照片不重新處理（批次重新壓縮
  全部既有資料風險大於好處，且既有資料佔比會隨時間下降）。
- 文字類資料上傳前可另外做無失真壓縮（類似 zip 原理），純粹減少傳輸量，不影響任何
  內容，值得直接做。

## 同步狀態顯示

- 顯示「上次同步時間」，一般情況顯示一個籠統的時間，例如「上次同步：14:32」。
- 若該次同步「部分成功、部分失敗」（例如文字資料同步成功、照片同步到一半失敗），
  拆開顯示細節，例如「文字資料：14:32　照片：同步失敗，還有 3 張未上傳」，不要用
  一個籠統的時間誤導使用者以為全部都同步好了。
- 時間顯示以雲端記錄的時間為準，不是裝置自己的時鐘。

## 錯誤與邊界情況處理

| 情況 | 處理方式 |
|---|---|
| 同步到一半斷網 | 已完成的部分保留，之後只補未完成的部分，不整批重來 |
| Google 登入過期／授權被收回 | 明顯、需要使用者處理才會消失的警示（不能是自動消失的
  toast），提示「登入已失效，請重新登入」 |
| 雲端資料夾被使用者手動改動/刪除、格式跑掉 | 整個停止同步並跳出警告，不嘗試「忽略壞
  掉部分繼續跑」，避免在猜測資料是否完整的情況下默默繼續 |
| 單張照片檔案本身損毀讀不出來 | 沿用現有匯出邏輯的既有模式：跳過這一張、標記失敗，
  不中斷整批同步 |

## 已知簡化（明確排除，非遺漏）

- 不做多使用者/多人共享同一份資料的協作系統（不是這次需求範圍）。
- 不做通用的「回上一步」復原功能，改用 Drive 版本歷史 + 刪除緩衝期取代。
- 不換成 WebP 圖片格式。
- 不重新處理既有（舊設定下）已上傳的照片。
- 不做「只同步近期資料、舊資料封存」這類資料生命週期管理——目前估算的資料量
  （一位老師約每月 10MB 上下）完全不需要這麼做。
- 離線版（`dist/TableC.html`）完全不受影響，不加任何登入/同步程式碼。
