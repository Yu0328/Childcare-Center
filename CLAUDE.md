# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

This repository is **implemented and in active use**, not in the design phase. `src/` holds a complete, working app. Every feature was built the same way — a design spec in `docs/superpowers/specs/`, an implementation plan in `docs/superpowers/plans/`, then subagent-driven implementation with task-by-task review. Keep following that workflow for new features: write a spec, then a plan, before touching code. The specs/plans directory is also the best place to look up *why* something is shaped the way it is — many non-obvious decisions (the tier→form-letter mapping, the Ⅵ tier's data source, why 適性紀錄 and 總表 have separate importers) are explained there, not just in code comments.

## What this project is

A local, browser-based tool for a childcare center (親子館) to digitize several paper forms:

1. **適性總表 (AssessmentForm / "C表")** — a per-age-tier developmental assessment log. A Child has many AssessmentForms; each pairs an age tier with a record period (year+month) and has many ObservationEntries (date, status, note) keyed to an indicator code. Status is one of `developed`／`developing`／`absent`（請假）／`courseChanged`（更換課程） — the latter two print in red with no ○/△ glyph (no strikethrough on this side, deliberately unlike 適性紀錄's exporter).
2. **適性紀錄(家長版) (ParentReport)** — a monthly parent-facing report: a 課程計畫表 (course-plan entries with dated occurrences, each occurrence optionally flagged `absent` and/or `courseChanged` — mutually exclusive in the UI), an 適性發展紀錄表 (narrative development-record entries per domain), 行為觀察 (behavior observations), and 點滴分享 (photo highlights).
3. **月計畫 (monthly course plan)** — a separate weekly/monthly activity-plan feature (`src/ui/monthlyPlanEditorView.js` and friends) with its own "請假／其他活動代替" override concept; unrelated to AssessmentForm/ParentReport's absent/courseChanged status and does not share code with them.

A 適性紀錄's course-plan data can be **彙整 (aggregated)** into a 總表, either creating a new one or merging into an existing one (`src/domain/aggregateCoursePlan.js`). An occurrence's `absent`/`courseChanged` flag carries into the aggregated ObservationEntry as status `'absent'`/`'courseChanged'` (absent wins if somehow both are set) rather than being dropped.

Staff previously filled these out by hand in Word, re-copying the same indicator text for every child.

## Architecture

- **Two build targets**, both from the same `src/`, via esbuild (`scripts/build.mjs` / `scripts/build-web.mjs`):
  - `npm run build` → `dist/TableC.html`, a single self-contained file for offline desktop use (open directly in a browser, no server).
  - `npm run build:web` → `site/`, a small PWA (service worker, manifest) for GitHub Pages / mobile use, since mobile browsers won't open a local `file://` HTML file directly.
  - **Deploy convention**: the repo root's own `index.html` and `sw.js` are a committed snapshot of a `build:web` run — GitHub Pages serves them directly from the default branch's root, not from `site/`. After any `src/` change meant to go live, rebuild with `npm run build:web`, copy `site/index.html` → `index.html` and `site/sw.js` → `sw.js` at the repo root, and commit both together (see git log for "public snapshot update" commits as examples). `site/` and `dist/` themselves are gitignored build output, never committed.
  - Both build scripts' inline bootstrap script must call `CFormApp.wireBackupControls({...})` first, capture its returned `{ updateLockState }`, and pass `{ onUnlock: backupControls.updateLockState }` to `CFormApp.mountApp(...)` — this is what keeps the header's 匯出備份/匯入備份 controls disabled until the password gate unlocks (see Security below). `src/app.js` itself does NOT auto-mount on load; both build scripts must call `mountApp` explicitly.
- **Storage**: browser IndexedDB (`src/storage/dbCore.js` + `db.js`/`parentReportDb.js`), plus an explicit export/import JSON backup (`src/storage/backup.js`) — the only way data survives the browser clearing its storage. A backup file is full plaintext PII (names, birthdates, notes, photos as base64), gitignored as `*_備份.json` (current filename, e.g. `2026-08-19_備份.json`) and `c-form-backup-*.json` (older filename, kept for any pre-existing files). `exportBackup()` returns an array of string parts (fed straight into `new Blob(parts)`) rather than one JSON string, and large imports go through `importHugeBackupFile()`'s streaming path — both exist specifically to avoid V8's ~536M-character string-length ceiling, which a large enough backup (many children's 點滴分享 photos) hits well before Safari's higher ceiling.
- **Password gate** (`src/auth/passwordGate.js`): a *soft deterrent* only, not real security — the check happens entirely client-side against a hash baked into the bundle, so it cannot stop someone who reads the source, and it does not encrypt anything already in IndexedDB. It exists to keep casual visitors out, not to protect data confidentiality. The header's backup export/import controls are gated on `isUnlocked()` (both at wire-time via `updateLockState()` and again inside each click/change handler as defense-in-depth) specifically because they sit outside `mountApp`'s password-gated container and would otherwise let anyone reach the raw data without ever entering the password.
- **docx export**: generated programmatically with the `docx` npm library (not a screenshot/print), so output is deterministic. Two exporters — `src/export/docxExport.js` (總表) and `src/export/parentReportDocxExport.js` (適性紀錄) — with different page layouts, column structures, flagged-status rendering (see above), and institution names; don't assume they share behavior.
- **docx import**: two parsers, `src/import/docxImport.js` (總表) and `src/import/parentReportDocxImport.js` (適性紀錄), both regex-based XML scanning of the raw `.docx` zip (not a real XML parser). Both normalize every extracted indicator code through `normalizeIndicatorCode` (`src/data/indicators.js`) before storing it, fixing codes typed with the wrong character set (ASCII Latin letters, or the specific known garbled mixed sequence "IⅤ") instead of the canonical Unicode Roman numerals the reference data uses.
- **Indicator reference data** (`src/data/indicators.js`): 178 developmental indicators across **6** age tiers (Ⅰ–Ⅵ; Ⅵ is "25個月以上", unbounded) × 5 domains, embedded as static JSON, sourced from the official practice guide — not user-entered. `TIERS[].formLetter` maps a tier to its exported filename letter; Ⅰ has none (no "X表" segment at all), Ⅱ→A, Ⅲ→B, Ⅳ→C, Ⅴ→D, Ⅵ→E — use `tierFormLabel(tierCode)` rather than reading `formLetter` directly. If you're ever unsure which tier a real file's own name implies, trust the file, not an assumption.
- Age tier is auto-suggested from (today − child's birthdate) via `src/domain/ageTier.js` but stays manually overridable per form, since staff sometimes backfill records for a tier the child has already grown out of.

## Version control

- `main` is the only long-lived branch and is the source of truth — it tracks `origin/main`, which GitHub Pages serves from. (It was renamed from a local-only `public` branch on 2026-08-18 after that branch and `origin/main` drifted apart; don't recreate a separately-named local branch for this.)
- Feature work happens on a worktree + branch per feature. Once a feature branch is reviewed and ready, fast-forward it into `main` and immediately delete the branch and worktree — don't leave finished branches lying around (this repo once accumulated 8 stale/superseded branches from skipping this step).
- After merging a `src/`-affecting change into `main`, immediately do the deploy snapshot (see Architecture above: `npm run build:web`, copy `site/index.html`/`site/sw.js` to the repo root, commit as one "public snapshot update") and push to `origin/main` right away. Don't let local `main` sit ahead of `origin/main` — a branch pushed straight to `origin/main` from elsewhere while local `main` lags behind is exactly how the split above happened.
- `master` is a frozen legacy branch (predates a history rewrite of what's now `main` — it shares no common ancestor with `main`). Keep it around for archival reference only; never merge it into `main` or build on top of it.

## Testing

- `npm test` (vitest + jsdom + fake-indexeddb). TDD is the norm here — check a sibling test file before writing a new feature to match existing conventions (fixture style, `waitFor` helper usage, hand-built zip fixtures for docx-parsing edge cases).
- **`npx vitest run` (and the bare `npm test`) picks up a second, stale copy of every test file** under `.claude/worktrees/*/tests/` if any such worktree exists locally — not committed, but easy to end up with. If a reported test count looks doubled, run `npx vitest run tests/` (scoped to the real directory) to get an accurate count for the current tree.
- **fake-indexeddb cannot round-trip a real `Blob`** through `addHighlightEntry`/`listHighlightEntriesForReport` — a stored Blob comes back as a plain `Object`, not `instanceof Blob`. Any test touching 點滴分享 photo export end-to-end needs a real browser (see below), not this test harness.
- **Round-trip testing is the standard rigor for import/export changes in this codebase.** Several real, non-obvious bugs (a Word vertical-merge continuation cell format mismatch, a paragraph-mark-only strikethrough false positive, a narrative that duplicated reference lines on every re-export, a ROC-date parser that only accepted dot separators) were only found by importing a real sample file, saving it unmodified, exporting it, re-importing that export, and comparing every field via multiset/key-based comparison (not positional — export commonly re-sorts) — not by unit tests alone, and not by "does it look right" spot checks. When touching either importer or exporter, do this against real files before calling it done. (The `references/` directory, gitignored, holds real sample files for exactly this.)
- For UI changes, build (`npm run build`) and drive the actual `dist/TableC.html` with Playwright (not installed as a project dependency — `npm install --no-save playwright` when needed; the Chromium binary is typically already cached locally) rather than assuming the vitest+jsdom suite alone proves the UI works.

## Sensitive files (gitignored, never commit)

- `references/` and any loose `*.docx`/`*.pdf` in the repo root — real reference samples containing actual children's names, birthdates, and behavioral records. Treat their contents as sensitive when discussing or logging; use them for testing but never quote a real child's data into a commit message, code comment, or this file.
- `*_備份.json` / `c-form-backup-*.json` — an app-exported backup is full plaintext PII (names, birthdates, notes, photos as base64) with no encryption.
